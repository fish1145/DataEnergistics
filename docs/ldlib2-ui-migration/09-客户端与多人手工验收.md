# 客户端与多人手工验收

## 验收边界

用户已确认客户端 UI 不要求新增自动测试。`Game Tests (Client)` 只提供隔离的真实客户端运行环境，Athena 继续仅属于 `clientTestRuntimeOnly`；不得把它加入生产 `runtimeClasspath` 或服务端 `testRuntimeClasspath`。最终客户端与多人结论由本表的真实操作、截图和日志共同确认，不能用客户端启动、JEI/EMI reload、JUnit 或服务端 GameTest 代替。

执行者只在完成实际操作后勾选条目。未执行、无法复现或缺少证据的条目保持 `[ ]`，失败项记录复现步骤和日志位置后回到对应实现修复。

## 环境准备

1. 在 IDEA Gradle 工具窗口执行 `Reload All Gradle Projects`。
2. 确认 `Game Tests (Client)` 优先使用 `data_energistics.clientTest` 模块，`Game Tests` 仍使用 `data_energistics.test` 模块。若空的 clientTest source set 被 IDEA 折叠到 test，先重新加载 Gradle且不要手改 `.idea` XML；最终以运行日志实际加载 Gradle 解析的 Athena `4.0.6` 为 classpath 判据，不通过扩大 Athena 依赖范围绕过。
3. 保持 `run/gametest/client/mods/athena-neoforge-1.21-4.0.0.jar.manual-backup` 的后缀不变，不得恢复成 `.jar` 造成 Athena 重复加载。随后启动 `Game Tests (Client)`，进入一次性创造模式测试世界。不要在正式存档执行自动搭建、拆除宿主或容量边界测试。
4. 在 `run/gametest/client/logs/latest.log` 确认 Athena `4.0.6`、LDLib2 `2.2.28`、Oritech `1.2.8`、JEI 和 EMI 均已加载，并确认没有 DataE 的 synthetic EMI recipe id 或 `emi.category.data_energistics.multiblock_preview` 翻译告警。
5. 准备以下物品；可从 Data Energistics 创造栏取得，也可使用对应 id：

| 用途 | 物品 id |
| --- | --- |
| Trinity 控制器与 XEI catalyst | `data_energistics:trinity_data_core` |
| Pattern Core 分页/退款 | `data_energistics:me_digital_pattern_processing_core`（64 槽；须成为已识别的 Trinity crafting structure 核心） |
| INPUT 舱室 | `data_energistics:composite_input_warehouse` |
| OUTPUT 舱室 | `data_energistics:composite_output_warehouse` |
| ME_INPUT 舱室 | `data_energistics:me_composite_input_warehouse` |
| ME_OUTPUT 舱室 | `data_energistics:me_composite_output_warehouse` |
| PATTERN_BUFFER 舱室 | `data_energistics:me_pattern_buffer` |

6. 另行准备可用的 AE 网络、Pattern Encoding Terminal、Universal Pattern Encoding Terminal、空白样板、容量卡，以及用于 fake slot、Shift-click 和拖拽分配的普通物品/流体/Key。

## JEI 与 EMI 多方块页

JEI 与 EMI 必须分别进入各自前端的 `data_energistics:multiblock_preview` 页面，页面设计尺寸为 `196x232`。canonical recipe id 是 `data_energistics:multiblock/trinity_data_core`；仅 EMI wrapper 的 synthetic id 是 `data_energistics:/multiblock/trinity_data_core`。若当前整合环境使用 JEMI 或其他桥接，仅验证同一个镜像页面不能同时算作两个 adapter 通过；证据中应能识别实际前端。快捷键由本地 JEI/EMI 配置决定，不在文档中假定固定按键。

| 编号 | 操作 | 通过条件 | 结果/证据 |
| --- | --- | --- | --- |
| X1 | 从 `data_energistics:trinity_data_core` catalyst/workstation 分别打开 JEI 与 EMI 多方块页面 | 两端 `196x232` 页面都出现非空 LDLib2 `Scene`、材料区和数量为 1 的 controller output，不出现空白画布或缺失纹理 | [ ] |
| X2 | 鼠标拖动旋转、滚轮缩放，并选择一个预览方块 | 相机交互稳定；选中位置、逻辑层、角色和候选信息与高亮方块一致 | [ ] |
| X3 | 在 `main`、`cpu`、`crafting` 之间来回切换 | 横向 selector 不溢出；标题、Scene、候选和材料同步变化；各子结构自己的选择被保留 | [ ] |
| X4 | 调整当前子结构的 `variantIndex`、tier、repeat 和 candidate | 每次合法变化都重建 Scene、fingerprint 和材料；控件不能越过定义范围；controller 级 recipe id 保持稳定 | [ ] |

## AE Processing Transfer

以下矩阵对原生 `ae2:pattern_encoding_terminal` 和 Universal Pattern Encoding Terminal 各执行一次，并分别从 JEI 与 EMI 发起。原生终端须安装在有电的 AE cable/network 上。通用终端使用 `data_energistics:universal_terminal` part，须已装入 Pattern Encoding Terminal；空手潜行右击切换到内部 `pattern_encoding` 模式后再普通右击打开，其菜单 id 为 `data_energistics:universal_pattern_encoding_terminal`。transfer 的职责到填配置为止，编码必须是后续独立动作。

| 编号 | 操作 | 通过条件 | 结果/证据 |
| --- | --- | --- | --- |
| A1 | 在 XEI 页面选择结构/tier/repeat/candidate 后点击 recipe transfer/fill | 终端切换为 Processing；input/output 与页面当前规范材料/controller output 完全一致 | [ ] |
| A2 | transfer 前记录空白样板、encoded slot、玩家背包和网络材料 | transfer 后四者均不变；没有调用编码，也没有搬运材料 | [ ] |
| A3 | 改变 tier/repeat/candidate 后立即再次 transfer | 使用点击瞬间的新 `currentRecipeView()`，不复用旧 ingredient cache | [ ] |
| A4 | 只改变 visibleLayer、formed、相机或 hover 后再次 transfer | Processing input/output 与改变前完全一致 | [ ] |
| A5 | 让终端预先带有普通 recipe source 或 Data Ripper key/fluid/display fallback，再执行多方块 transfer | 成功后旧临时状态全部清空，普通 Processing 配置不被历史状态重排 | [ ] |
| A6 | 制造实际容量不足、filter 拒绝或 stale page 条件 | 返回可见错误；mode、input/output、source/key/fluid/display 和样板槽零变化 | [ ] |
| A7 | transfer 成功后点击 AE 自带编码按钮 | 此时才消耗/覆盖空白样板并生成一份普通 Processing Pattern | [ ] |
| A8 | 检查编码结果 | 仅包含普通 stack/amount；不存在 structureKey、variantIndex、tier/repeat、candidate、visibleLayer、方向、镜像或 BlockState metadata | [ ] |

81 个 input 成功、82 个 input 原子失败以及故障注入回滚已由逻辑/服务端测试覆盖；若当前 Trinity 定义无法在真实页面产生该边界，手工验收不要求伪造结构或修改 catalog。

## 多人验收

使用与客户端相同分支和依赖启动开发服务器，再以至少一个真实客户端连接。需要验证双端状态的条目不得由集成单人世界代替。

| 编号 | 操作 | 通过条件 | 结果/证据 |
| --- | --- | --- | --- |
| M1 | 客户端打开四窗，拖动/置顶/Esc/关闭/重开 | client/server 动态 membership 和 sequence 一致；没有残留窗口、重复 RPC 或断线 | [ ] |
| M2 | 一名玩家操作退款/自动搭建，另一名玩家观察宿主和库存 | 服务端权限、距离、host identity 和一次性请求生效；其他玩家不能越权或重放 | [ ] |
| M3 | 在 transfer 前后让服务端替换菜单/host、断开连接或卸载区块 | stale container 被拒绝；终端零部分覆盖；不完整恢复时菜单失效/关闭 | [ ] |
| M4 | 两名玩家分别打开同一类舱室并进行合法槽位操作 | 容量、fake slot、只读槽和实际库存同步一致，无复制、丢失或客户端假状态 | [ ] |
| M5 | 客户端关闭页面、退出服务器并重新连接 | 所有 Scene、dummy world、菜单树和窗口资源 exactly-once 释放；重连后创建新实例 | [ ] |
