# AE 样板写入设计

## 已确认语义

借鉴 GT/ECO 的 XEI 多方块 wrapper 展示模式，由 Data Energistics 额外定义普通 recipe projection 与 typed transfer。GT 没有多方块 AE writer，ECO 的 upload 又明确拒绝 Processing 模式，二者都不能作为完整编码实现。给定当前 `structureKey`、`variantIndex`、tier、repeat 和 candidate selections 后，结构投影自动产生一份普通 XEI 配方：

| 配方角色 | 内容 |
| --- | --- |
| input | 展开结构所需材料，按 ItemStack 组件归一化并合并数量 |
| output | 该多方块定义的控制器/owner 物品，数量为 1 |
| registered recipe id | controller 级稳定 ID；页面内选择改变时保持不变 |
| projection fingerprint | definition revision、structureKey、variantIndex、tier/repeat 与 candidate selections 的稳定摘要 |

这不是 AE 专属配方、不是新的建造蓝图 item，也不新增 AE pattern details。“写入样板”必须拆成两个动作理解：JEI/EMI transfer 只把这份普通配方填入 AE Pattern Encoding Terminal 的 Processing 配置输入/输出；只有用户随后点击 AE 自带编码按钮，既有菜单才调用原有编码流程生成普通 Processing Pattern。transfer 本身不得编码。

样板是通用材料配方，不是结构状态快照。`structureKey`、`variantIndex`、tier/repeat 与 candidate selections 会通过最终普通 Item/Fluid stack 和 amount 改变样板内容，但这些选择标识本身不得作为 metadata、custom pattern details 或 `BlockState` 编码进样板。`visibleLayer`、formed、方向、镜像、相机和逐方块属性也不进入样板。搭建发生时，由独立 `BuildRequest` 携带 structure/variant/build options，服务端按权威定义自动生成需要放置的精确状态；服务端不得从普通 Processing 样板反推结构身份。

## 转换链路

1. `PreviewSelection` 经过结构投影生成 `StructurePreviewSnapshot` 和对应 `projectionFingerprint`。
2. recipe mapper 从快照取得材料汇总，并从定义取得 controller/owner output。
3. 仅规范材料汇总 `ItemSlot` 标为 XEI input，controller/owner 规范槽标为 output；Scene、候选检查器、谓词/hover/层级控件全部为 role NONE。
4. JEI/EMI typed transfer handler 直接读取点击瞬间的 `currentRecipeView()`，请求只携带受限的 recipe identity/selection/fingerprint。服务端从当前 catalog 权威重建材料，并按目标终端真实 `ConfigInventory.size()`、`isAllowedIn()`、`getMaxAmount()` 验证槽位、空栈和数量；协议上限仍为 81 input/27 output。只有全部通过后才原子切换 Processing 模式并填充配置槽。
5. 同一事务在发布前快照并清空 pending/last source、Data Ripper key/fluid 和 display fallback；清空后必须读回验证。任何后续失败都把这些字段与 mode/input/output 一起恢复。
6. 玩家使用既有编码操作生成普通 AE Processing Pattern；空白样板、覆盖和网络库存行为完全沿用现有菜单。
7. 后续实际搭建独立提交 structureKey、variantIndex、tier/repeat、方向等 build options；精确放置状态必须现场从权威结构定义解析，不能从 AE 样板反序列化。

## 参数与显示层

`structureKey`、`variantIndex`、tier、repeat 和 candidate selections 会改变普通配方，因此 transfer 必须读取点击时的当前 recipe view。`visibleLayer`、相机、hover、选中方块和 formed toggle 只是视图状态，不改变 input/output。

同一控制器页面默认只 transfer 当前正在预览的子结构配方，不得隐式合并全部子结构。组合结构不是首轮范围；若未来另行加入，必须定义独立 recipe view、共享材料去重和清晰标题，不能复用当前 fingerprint 冒充单子结构。

## 容量与候选规则

1. input 按 `ItemStack.isSameItemSameComponents` 等价语义聚合，不能只按 item id 合并。
2. predicate 有多个候选时，recipe view 使用当前选定候选；未选定时使用定义提供的稳定默认候选。候选 inspector 槽自身保持 XEI role NONE，只有重算后的规范汇总槽参与 transfer。
3. 输入种类超过 81 或输出种类超过 27（以及目标终端实际容量更小时），transfer 必须在任何菜单变更前返回可见错误，不截断、不拆成语义不完整的多个样板。
4. 数量超过单个 `GenericStack` 可表示范围时 Fail Fast；不得静默饱和或溢出。
5. 资源重载后 recipe view 失效并重建，旧页面不得 transfer 已过期材料。

## 复用现有编码入口

Data Energistics 已有普通 Pattern Encoding Terminal、Universal Pattern Encoding Terminal 的 Processing 编码，以及 JEI/EMI transfer 后的 source/key/fluid 记忆逻辑。当前实现提供正常的 typed recipe/ingredient 入口让这些逻辑消费，不新增反射，不直接写 `encodedPatternSlot`，也不复制空白样板消耗逻辑。

LDLib2/JEI 初次 recipe setup 会建立 formal ingredient slots；当前实现把 JEI ingredient 变化合并为延迟请求，再调用公开 `showRecipes` 重建页面/formal slots，并接受导航历史增加，同时为 EMI 接入 live `getInputs()`/`getOutputs()` 和槽池扩容刷新。动态材料因此可以随结构选择更新展示，但展示刷新不改变 transfer 信任边界。动态选择的 transfer 唯一权威来源仍是 wrapper/session 在用户点击瞬间暴露的 typed `currentRecipeView()`；handler 校验当前 projection fingerprint 后再建立原子变更计划。registered recipe id、显示层、相机、候选辅助槽、formal slots 或 ingredient cache 均不能替代当前 recipe view。

transfer 不执行物料搬运：它写入的是 AE Processing 配置库存中的普通 `GenericStack` 描述，不从玩家背包、ME 网络或 XEI 页面提取材料。它也不读取、清空或写入 `encodedPatternSlot`，不消耗空白样板，不调用 `encode()`。这些业务只在用户主动点击 AE 编码按钮后由既有 AE 菜单处理。

## Source 状态隔离

Pattern Encoding Terminal 还可能保留前一次 recipe transfer 的菜单临时状态。普通多方块配方不携带这些信息，若只覆盖 Processing input/output，会让后续编码错误继承旧 workstation 或 Data Ripper 特殊栈。因此它们必须与配置库存属于同一原子事务：

| 状态 | 成功 transfer | 失败 transfer |
| --- | --- | --- |
| pending pattern source | 清空 | 恢复快照 |
| last encoded pattern source | 清空 | 恢复快照 |
| pending key input/output | 清空 | 恢复快照 |
| pending fluid input/output | 清空 | 恢复快照 |
| displayed key input/output fallback | 清空 | 恢复快照 |
| mode、Processing input/output | 写入新普通配方 | 恢复快照 |

`PatternEncodingMultiblockTransferState` 是以上 source/key/fluid/display 字段的不可变快照，集合和 `GenericStack` 做防御性复制。成功路径调用 clear 后必须再次 snapshot 并验证 `isClear()`；回滚路径 restore 后必须与原快照相等。任一恢复或验证失败都作为 suppressed failure 保留并使菜单失效或关闭，不能继续编码不可信状态。

XEI Data Ripper resolver 只在显式对象是 `DataRipperReassemblerRecipe`，或是持有该 recipe 的 `RecipeHolder` 时返回结果；不再从 XEI 上下文、显示文本、历史 source 或模糊提示解析 Data Ripper。编码前的自动 key 解析还要求 pending source 明确指向 Data Ripper；多方块 transfer 清空该状态后不会进入这条特殊路径。这样普通多方块 Processing Pattern 不会被旧 Data Ripper key/fluid 布局重排。

## 当前实现状态

截至实现锚点 `b5780774`（文档提交位于其后），以下实现均已按 common/network、JEI、EMI 和 UI 功能边界拆分提交：

1. `MultiblockPatternTransferRequest` 和 bounded payload/codec 携带 container id、稳定 registered recipe id 与完整 projection fingerprint；字符串、revision、variant、repeat、tier、candidate 数量和值均有限制，拒绝重复 key 和 trailing bytes。失败日志使用独立有界上下文，只记录 identity 和 selection 数量，不展开客户端 map/value。
2. 服务端 handler 校验 exact current container/menu、`isValidMenu()` 与 `stillValid()`，再按当前 catalog 权威重建 `MultiblockRecipeView`。客户端不提交可信材料栈，stale revision 或未知 controller/structure/variant/tier/repeat/candidate 直接失败。
3. `PatternEncodingMultiblockTransfer` 先使用目标终端真实配置库存完成全量预检，再 snapshot source/key/fluid/display 状态，对 input/output 开启 batch，清空尾槽、写入并逐槽读回。发布前清空菜单临时状态并验证；任何前向失败、状态清理失败、模式切换失败或 `endBatch` 失败都会恢复原 mode、全部槽和完整临时状态。
4. 成功路径只切换 `PROCESSING`、填入配置、清空旧 source/key/fluid/display 并 `broadcastChanges()`；不调用 `encode()`、不访问 `encodedPatternSlot`、不搬运物料。回滚异常作为 suppressed 保留，不完整回滚使菜单失效或关闭。
5. JEI 已为原生与 Universal 菜单注册精确 typed handler，点击时只读取一次 `currentRecipeView()`，并在发请求前处理 source/identity、slot filter、`maxAmount` 和菜单访问异常；失败返回可见 user error。可选 `ae2jeiintegration` 的直接引用隔离在独立类并受 mod-loaded 条件保护，不使用反射。定向 JUnit 7/7 通过。
6. EMI handler/core/guard/mixin 只在 `FILL_BUTTON` 接管 DataE typed live recipe；具体 `EmiEncodePatternHandler` 的 `supportsRecipe` 覆盖继承的 catch-all，使 AE2 原 handler defer 而不影响其他 recipe。拒绝路径记录日志，定向 JUnit 7/7 通过。
7. JEI 动态 ingredient 采用延迟合并刷新并最终调用公开 `showRecipes` 重建页面，runtime stop 时释放 category `uiCache` 并允许后续重新注册；EMI 的 `getInputs()`/`getOutputs()` 始终读取 live recipe view，槽池扩容后延迟 `focusRecipe`。这些刷新只保证页面跟随选择，不参与服务端信任或 transfer 决策。
8. 最终 `spotlessCheck compileJava compileTestJava test runGameTestServer build` 已通过，服务端 GameTest 为 367/367，本地质量审计也已完成。文档提交/推送、Draft PR CI 和客户端验收仍按实际状态继续。

客户端 GameTest 在启动阶段因 Oritech 的 Athena 运行时依赖缺失而阻塞。不得通过修改依赖绕过，也不得用上述服务端/JUnit 结果宣称 JEI/EMI 实际按钮交互已经验收；外部运行环境修复后补跑。

## 验收矩阵

| 场景 | 断言 |
| --- | --- |
| 默认子结构 | XEI input 等于快照材料，output 等于 controller/owner |
| 修改 tier/repeat | 页面材料与 transfer 后终端槽同时更新 |
| 修改 structure/variant/candidate | fingerprint 和规范材料更新，registered recipe id 保持稳定 |
| 动态 ingredient 已刷新 | JEI/EMI 页面显示当前材料，但 transfer 仍只接受点击瞬间的 `currentRecipeView()`，不把展示缓存当权威 |
| 修改显示层 | 配方与终端槽不变 |
| 候选检查槽 | 不出现在 input/output；只有其选择造成的规范材料结果进入样板 |
| JEI 与 EMI | transfer 后得到相同 Processing input/output |
| 候选方块切换 | 配方只替换对应材料，数量重新归一化 |
| 超出终端容量 | 显示 transfer 错误，终端原状态不被部分覆盖 |
| transfer 成功 | 只填 Processing 配置并切换模式；不编码、不碰 encodedPatternSlot、不消耗样板、不搬物料 |
| transfer 前存在旧 source/key/fluid/display | 成功后全部清空；普通多方块配方不受旧 workstation 或 Data Ripper 状态污染 |
| 清理临时状态后发生故障 | mode、input/output、pending/last source、key、fluid、display 全部恢复原快照 |
| 普通多方块 recipe 进入 Data Ripper resolver | resolver 返回空，不按 Data Ripper 布局重排 |
| 用户点击 AE 编码 | 走现有菜单流程，恰好产生一份普通 AE Processing Pattern |
| 检查已编码内容 | 只含普通 stack/amount；不存在 structureKey、variantIndex、tier/repeat、visibleLayer、方向、镜像或 BlockState metadata |
| 回滚再次失败 | 保留 primary failure 和 suppressed rollback failure，菜单失效或关闭，不继续使用不可信配置 |
