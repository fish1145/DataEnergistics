## 四窗视觉与生命周期基线

1. `TrinityHostedWindowChrome` 统一四窗为 `292x210`，顶部标题使用固定边界和 `HOVER_ROLL`，关闭命令使用图标按钮，标题面提供拖动；左侧 `196px` 是各窗口独享的预览列，右侧 `84px` 是状态或动作列。
2. `main`、`cpu`、`crafting` 的状态行尺寸固定，超出内容在纵向 `ScrollerView` 中滚动，单行长文本在自身边界内滚动且裁切；crafting 的退款按钮保留在动作列底部。
3. `auto_build` 的结构选择、build-requested 开关和确认命令位于同一 `84px` 动作列。开关与确认长文案的文本宽度固定为 `62px`，使用 `HOVER_ROLL` 且隐藏 overflow；开关标签只响应鼠标左键，并且一次点击只能切换一次。
4. launcher rail 以 important `z-index: 400` 固定在 hosted windows 之上。四窗可同时挂载，每窗必须持有独立 provider generation、`StructurePreviewSession` 和 `Scene`；关闭恰好释放自己的资源，重开创建新 generation、新树和新 Scene，不影响其余三窗。
5. host 只对“首次且没有保存位置”的完全遮挡做默认碰撞级联。在最小 `320x240` GUI 中，四个 `292x210` 新窗口依次为 `(4,4)`、`(11,11)`、`(18,18)`、`(24,25)`；已保存位置和用户拖动位置优先，互不重叠的默认位置不应被级联改写。

## 四个 Provider 边界

| Key | 状态来源 | UI 职责 | 唯一允许的业务动作 |
| --- | --- | --- | --- |
| `main` | 客户端 `TrinityDataCoreMenu` 的 online、main formed/matched/failure、storage type/amount/capacity 同步字段 | 展示主机与主结构状态，并创建独立主结构预览 view state | 无世界或库存写入 |
| `cpu` | 菜单的 CPU formed/matched/failure、partition/busy partition、storage bytes、co-processors、busy crafting CPU 字段 | 展示 CPU 子结构和容量；明确区分全网 busy crafting CPU 与 Trinity CPU partition | 无世界或库存写入 |
| `crafting` | 菜单的 crafting formed/matched/failure、P Core count/capacity、crafting target、refundable 状态 | 展示合成子结构、目标 tooltip 与退款按钮 | 退款仅调用 `menu.sendRefundAll()`，由既有服务端 client action 调用 host |
| `auto_build` | 每次打开重新取得 preview catalog/spec；窗口内保存三结构各自 tier/repeat 暂存状态 | 选择结构、tier/repeat、展示权威计划并显式确认 | `TrinityAutoBuildDraft -> TrinityAutoBuildSubmission -> TrinityHostedAutoBuildPayload -> TrinityAutoBuildRequest`，由服务端 resolver 重建并校验 |

provider 不读取客户端 BlockEntity，不缓存跨 revision 的 spec，也不共享元素树、`Scene`、dummy world 或拖动状态。四个 provider 可以共同委托纯 `StructurePreviewUiFactory`，但 host 和 XEI 必须各自创建新的调用上下文及运行时资源。

## 自动建造细节

Trinity 多方块主机共有四个独立子 UI：`main`、`cpu`、`crafting` 三个结构窗口和一个自动搭建窗口。四窗可同时打开并独立拖动，点击窗口提升 z-order，Esc 每次只关闭最上层窗口；关闭和重开任一窗口不得影响其他三个窗口的选择、位置或资源。

`TrinityDataCoreAutoBuildPanel` 只维护 `TrinityAutoBuildDraft` 暂存选择；点击确认时生成不可变 `TrinityAutoBuildSubmission`，经 `TrinityHostedAutoBuildPayload` 发送后由服务端 resolver 重建并校验 `TrinityAutoBuildRequest`。自动搭建作为第四个 provider 通过 host 扩展层非模态挂载，不作为结构窗口页签。关闭时必须 `removeChild`，重开时创建全新元素树，不复用旧监听器、拖动对象或其他窗口实例。

必须在服务端重新验证：structure key/variant、definition revision、repeat count 的上下界、tier 是否存在、玩家距离与权限、目标区块已加载、物品库存、方块可替换性、结构世界状态、菜单/host 仍有效，以及 lifecycle/request sequence 未重复或乱序。任一恶意或过期请求失败时不得写世界、部分消耗材料或保留半完成 session；客户端禁用按钮只用于体验，不能构成校验。

普通 AE Processing Pattern 不保存结构身份、方向、镜像或精确 `BlockState`。只有玩家实际确认自动搭建时，`auto_build` 才提交独立 build request；服务端在这一刻按当前权威定义、选择和世界条件自动补全放置状态。不得从 AE 样板恢复或推测搭建状态。
