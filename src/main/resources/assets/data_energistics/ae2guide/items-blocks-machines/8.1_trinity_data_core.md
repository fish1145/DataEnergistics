# Trinity Data Core

The Trinity Data Core is a multiblock system made of<br>
**a main structure, a CPU child structure, and a crafting child structure**.<br>
All three sections must pass validation before the host publishes its AE2 storage, crafting CPUs, and pattern-provider services.

## Three Structure Sections

| Structure | Role | Valid core blocks |
| :--- | :--- | :--- |
| Main structure | AE storage capacity and storage-type capacity | Digital Storage Cores, Empty Trinity Units |
| CPU child structure | Virtual crafting CPUs, crafting storage, and threads | Merged Digital Storage Cores, Empty Trinity Units |
| Crafting child structure | Physical pattern-core capacity | Digital Pattern Processing Cores, Extended Pattern Processing Cores, Overlimit Pattern Processing Cores, Empty Trinity Units |

An Empty Trinity Unit can occupy a structure position without contributing capacity, which lets you build the structure first and replace tiers later. Core families are not interchangeable: storage cores belong to the main structure, merged cores belong to the CPU child structure, and pattern cores belong to the crafting child structure.

## Building The Structure

Place the Trinity Data Core and open its **Structure Builder** to inspect all three previews, missing blocks, and current tier selections. Configure the sections in this order:

1. Select the storage-core tier for the main structure.
2. Select the merged-core tier and repeat count for the CPU child structure.
3. Select the pattern-core tier and repeat count for the crafting child structure.
4. Confirm that the preview has no blocking blocks, missing blocks, or unloaded chunks before starting the automatic build.

The main structure can be built once. The CPU and crafting child structures support repeat-count selections from **1 to 12**. Automatic building validates the complete transaction; a failed request does not publish a partially formed structure.

The definitions validate orientation, layer counts, core families, and Empty Trinity Units. After a manual build, reopen the host menu to inspect formed state, matched-block counts, failure reasons, and failure positions for each section.

The main structure declares **1,176 storage-core slots**. Each Digital Storage Core contributes total capacity and storage-type capacity according to its tier:

| Core tier | Per-core capacity |

Total capacity is the sum of every installed storage core. Type capacity is the sum of their type capacities. Unlimited storage is granted only when every declared slot contains a maximum-tier 256M Digital Storage Core; empty units or lower tiers produce a finite profile.

The host menu displays stored amount, total capacity, type capacity, and storage priority. It follows AE2 priority semantics: lower values are preferred for extraction, while higher values are preferred for insertion.

## CPU Child Structure: Parallel Crafting

The CPU child structure uses merged cores to provide crafting storage and virtual CPU partitions. The repeat height controls available threads, up to **256 threads**; each filled merged core contributes its tier's crafting-storage capacity.

- The CPU child needs at least one valid repeated layer and one valid merged core.
- Thread count increases with the continuous repeat height and is capped at 256.
- Filling every CPU core position with 256M merged cores and reaching the maximum repeat height produces the unlimited CPU-storage profile.
- A valid CPU contribution is published as multiple virtual AE2 crafting CPUs; resources are not incorrectly divided between workers.
- An unformed child structure or unavailable main storage prevents the CPU from being published.

The host menu reports CPU structure state, virtual CPU count, crafting storage, and co-processor information.

## Crafting Child Structure: Patterns

The crafting child structure supports three pattern-processing core tiers:

| Pattern core | Pattern capacity per core |
| :--- | ---: |
| Digital Pattern Processing Core | 72 |
| Extended Digital Pattern Processing Core | 144 |
| Overlimit Digital Pattern Processing Core | 576 |

Total pattern capacity is the sum of all mounted pattern cores. Physical pattern slots are aggregated into one published catalog and exposed to AE2 through the Information Exchange Depot.

Pattern cores have their own management UI. During structure removal, core replacement, or catalog changes, the old layout is retained while maintenance completes; installed patterns, queued inputs, and pending outputs are not silently discarded by a structural recheck.

## Information Exchange Depot

The Information Exchange Depot is the network endpoint for the Trinity system. It must be part of a valid Trinity structure and bound to the host before the host can publish storage and crafting services.

The depot has three modes:

- **Storage**: mount Trinity storage on the AE2 network;
- **Input**: route network input into Trinity storage;
- **Output**: push Trinity storage contents back to the network.

One structure owns an exclusive access lease for its active depot, preventing several depots from publishing duplicate storage, CPU, or pattern services for the same host. The depot menu reports binding, storage, crafting CPU, and pattern-processing state.

## Patterns And Crafting

1. Install processing patterns in the pattern cores of the crafting child structure.
2. Confirm that the crafting and CPU child structures are formed and that the Information Exchange Depot is online.
3. Submit a crafting request through the AE2 network.
4. The host selects a route using the aggregate pattern catalog and virtual CPU partitions.
5. Inputs enter Trinity storage through the depot, the pattern cores execute the selected patterns, and outputs return to the AE2 network.

The host UI provides pattern search, pattern priority, storage priority, and queued-content refund actions. Pattern priority applies to the aggregate Trinity provider; higher values are preferred during planning.

## Diagnostics And Maintenance

The host UI reports formed state, matched-block counts, failure reasons, and failure positions for the main, CPU, and crafting structures. When a section is unformed, check:

- controller orientation and the structure's front direction;
- layer counts and repeat selections;
- core families assigned to the correct structure;
- unsupported cores or missing Empty Trinity Units;
- unloaded chunks around the structure;
- Information Exchange Depot binding and online state.

Before removing or replacing a pattern core, use the pattern-refund and retained-item-refund actions in the host UI. Queued inputs and pending outputs are written back to AE storage first, then delivered to the player's inventory or dropped in the world if necessary.
